This document supersedes all previous MD-001 drafts.

============================================================
1. OBJECTIVE
============================================================

Build a reproducible demonstration of independently
controlled technical domains producing, conveying, and
verifying domain-generated artifacts without requiring:

- Shared execution state
- Shared authorization logic
- Disclosure of internal execution logic
- Centralized verification authority
- Producer availability during subsequent verification
- Intermediary participation in verification decisions

MD-001 concerns VERIFICATION EVIDENCE, not execution
authority.

A verification artifact may be independently verified
more than once without granting permission to repeat
the underlying operation.

The baseline contains:

B01 — Cross-domain artifact verification
B02 — Producer-offline stateless verification
N01 — Tampered artifact rejection
X01 — Required disclosure inventory (unscored)

A physical execution-isolation extension is designed
separately and is not a prerequisite for the baseline.

Do not expand the scope without operator approval.

============================================================
6. ARTIFACT FORMAT
============================================================

Domain A performs a defined local software operation.

At a provider-defined event boundary, Domain A produces
a signed verification artifact.

Minimum proposed signed fields:

- Artifact format version
- Producer domain identifier
- Key identifier
- Unique artifact identifier
- Operation/event identifier
- Asserted outcome

Include a cryptographic signature covering the
canonical representation of those fields.

Additional fields require justification.

Define deterministic canonical encoding.

Specify:

- Exact signed bytes
- Field types
- Encoding rules
- Signature algorithm
- Key identifier mapping
- Verification behavior for malformed input

Use Ed25519 where compatible with the frozen reference.

Domain B must validate:

- Artifact structure
- Cryptographic signature
- Trusted producer/key binding
- Artifact integrity
- Applicable local acceptance criteria

A key identifier is a selector, not proof of trust.

The verifier must use a locally provisioned trusted
mapping of producer identity to public verification key.

Document how that trust anchor was provisioned.

Trust-anchor provisioning is out-of-band configuration,
not a shared authorization session.

Domain B must not require:

- Domain A's private key
- Domain A's internal database
- Domain A's execution logic
- Domain A's live session state
- Online access to Domain A

Timestamps may appear in evidence records.

Do not use wall-clock timestamps as verification inputs
in this baseline.

Use disposable test signing keys.

Preserve test keys and exact reproducibility bytes
according to existing Xer0trust publication conventions.

============================================================
7. VERIFIER STATELESSNESS
============================================================

Domain B evaluates each artifact independently.

The verifier must not:

- Record previously seen artifact IDs for acceptance
  or rejection
- Mark artifacts SPENT
- Consume artifacts
- Deny an artifact merely because it was verified before
- Depend on an earlier verification session
- Contact Domain A for a fresh decision

Local trust configuration may persist.

Verification results may be written to separate
evidence logs.

Evidence logging must not influence subsequent
verification decisions.

B02 must perform a new cryptographic verification,
not return a cached result.

Repeated artifact verification does not grant
execution authority.

============================================================
9. B01 — CROSS-DOMAIN VERIFICATION
============================================================

OBJECTIVE:

Demonstrate independent verification of an artifact
produced in another technical domain.

PROCEDURE:

1. Domain A performs a defined local operation.

2. Domain A generates a signed artifact representing
   the operation's asserted outcome.

3. Domain A sends the artifact through NUVL.

4. NUVL forwards the artifact without modifying its
   signed content.

5. Domain B receives the artifact.

6. Domain B performs independent verification using
   its locally provisioned trust anchor and criteria.

EXPECTED:

- Artifact arrives unchanged.
- Signature verification succeeds.
- Producer/key binding is valid.
- Domain B accepts the artifact.
- Domain B requires no producer execution state.
- NUVL makes no verification decision.

REQUIRED EVIDENCE:

- Producer operation record
- Original signed artifact
- Producer-output SHA-256
- Relay ingress observation
- Relay egress observation
- Verifier-ingress SHA-256
- Verification decision
- Applicable firewall rule export
- Logged denied direct A-to-B connection attempt
- Approved-path connectivity observations

Compare hashes only where the same artifact bytes
have actually been observed.

PASS requires successful independent verification,
a demonstrated relay path, and no unexplained artifact
modification.

============================================================
10. B02 — PRODUCER-OFFLINE VERIFICATION
============================================================

PREREQUISITE:

B01 PASS.

OBJECTIVE:

Demonstrate that Domain B can independently verify
the same artifact after Domain A becomes unavailable
and the verifier process is restarted.

PHYSICAL PROCEDURE — LATER SCORED RUN:

1. Preserve the B01 artifact.

2. Record the existing verifier process identity.

3. Power off Domain A.

4. Record operator observation of power-off.

5. Attempt a connection to Domain A's expected
   endpoint and record the failed connection.

6. Restart Domain B's verifier process.

7. Record the new verifier PID and process-start
   information to establish a fresh process.

8. Verify the original B01 artifact again.

9. Record the new cryptographic verification result.

EXPECTED:

- Domain A remains unavailable.
- Domain B has no previous verification session.
- Original artifact verifies successfully again.
- The verifier performs a fresh signature check.
- No producer connection is required.
- No previously-seen-artifact rule is applied.

Persistent local trust-anchor configuration is allowed.

Verification evidence logs may persist but must not
be consulted to determine acceptance.

OFFLINE BUILD:

Simulate producer unavailability and verifier restart.

Clearly label simulation results.

Do not claim that offline simulation proves physical
power-loss behavior.

============================================================
11. N01 — TAMPERED ARTIFACT
============================================================

OBJECTIVE:

Demonstrate rejection of a modified signed artifact
without modifying the NUVL relay.

PROCEDURE:

1. Produce a valid signed artifact.

2. Forward the original artifact through NUVL.

3. Pass it to a separate test-only tampering adapter
   downstream of NUVL.

4. Modify one signed field without producing a
   replacement valid signature.

5. Deliver the modified artifact to Domain B.

6. Record Domain B's verification decision.

EXPECTED:

- Original artifact verifies successfully.
- Modified artifact fails verification.
- Domain B rejects the modified artifact.
- Original and modified artifact hashes differ.
- NUVL source remains unchanged.

REQUIRED EVIDENCE:

- Original artifact
- Modified artifact
- Mutation description
- Original SHA-256
- Modified SHA-256
- Verification rejection
- Adapter configuration
- Relay source integrity check

The tampering adapter is separate test infrastructure.

It must not create an alternate bypass around NUVL.

Do not incorporate the adapter into the frozen forwarder.

============================================================
18. CLAIM AND PUBLICATION LIMITATIONS
============================================================

MD-001 is intended to demonstrate:

- Cross-domain artifact conveyance
- Independent verification
- Producer-offline verification
- Stateless verification behavior
- Detection of artifact modification
- Defined disclosure boundaries

It does not independently establish:

- Truth of the asserted underlying event
- Universal absence of information disclosure
- Security of all artifact formats
- Production readiness
- Authorization replay resistance
- Physical execution isolation before witness testing
- General cryptographic security beyond tested behavior

Verification of an artifact is not authorization
to execute an operation.

A valid signature authenticates signed assertions
under the trusted key; it does not independently
prove the underlying event occurred.

Do not describe offline simulations as physical results.

Do not describe future tests as completed.

Map final claims to the actual utility disclosure
before public publication.
