# AE001 Preflight Evidence

This directory preserves the AE001 preflight history that preceded the scored campaign.

It contains two preflight runs:

| Run | Status | Purpose |
|---|---|---|
| `AE001_PREFLIGHT_20261018_R1` | INCOMPLETE | First campaign attempt; stopped before deployment because the Windows source-transfer command exceeded the command-line length limit |
| `AE001_PREFLIGHT_20261018_R2` | PASS | Completed four-case preflight after source transfer was changed to SSH standard input |

Preflight evidence is retained separately from scored evidence.

## R1 — Incomplete Before Deployment

`AE001_PREFLIGHT_20261018_R1/` preserves the first attempt.

The harness stopped before any AE001 case executed with:

```text
FileNotFoundError: [WinError 206] The filename or extension is too long
```

The failure occurred because an encoded source bundle exceeded the Windows command-line length limit.

This was a campaign-harness transport failure, not a scored failure of the AE001 property.

R1 therefore contains no executed AE001 cases and is classified **INCOMPLETE**.

Its original harness is retained under:

`../retained/PREFLIGHT_R1/run_ae001.py`

## R2 — Completed Preflight

`AE001_PREFLIGHT_20261018_R2/` contains the completed preflight.

Overall result: **PASS**

The four preflight cases were:

| Case | Provider B outcome | Result |
|---|---|---|
| B01 | START → one software execution → COMPLETE | PASS |
| N01 | DENY `auth_bad_sig`; execution/state unchanged | PASS |
| N02 | DENY `auth_provider_mismatch`; execution/state unchanged | PASS |
| B02 | START → one software execution → COMPLETE | PASS |

R2 demonstrated that the intended deployment, transport path, provider behavior, evidence collection, state inspection, and provider-signature verification were functioning before scored execution.

The R2 harness is retained under:

`../retained/PREFLIGHT_R2/run_ae001.py`

## Pre-Score Correction

After R2 completed, inspection identified a scoring-logic edge case in the harness.

An authenticated unexpected admission during a rejection case needed to be classified as **FAIL** even if excess boundary events were also present.

That classification branch was corrected before the scored-run freeze.

The correction did not change:

- provider implementation;
- relay implementation;
- artifact format;
- request binding;
- provider authority;
- the four-case matrix; or
- expected case outcomes.

The corrected final harness is published under:

`../../scripts/run_ae001.py`

## Evidence Separation

Preflight runs are not the scored result.

They are retained to show campaign development, setup verification, and corrections made before scoring.

The scored evidence is under:

`../scored/AE001_SCORED_20261018_R1/`

That directory contains the locked scored run used for the AE001 result.

## Preservation

The preflight directories preserve the artifacts generated by each run rather than rewriting earlier attempts after later corrections.

This allows the publication to distinguish:

- setup or harness failures;
- successful preflight behavior;
- pre-score corrections; and
- the final scored evidence.

## Scope

No architectural claim is derived from R1.

R2 established preflight readiness only.

The AE001 result itself is established by the separately frozen scored run, not by these preflight directories.
